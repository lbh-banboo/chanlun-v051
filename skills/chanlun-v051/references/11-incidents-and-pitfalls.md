# 11 · 事故、坑与排查手册

> 这一章汇总**这类工具链常见的故障模式**，按"现象 → 根因 → 修法 → 如何避免"写；现象均已泛化，不含任何具体运行环境或日期。
> 你的环境不同，细节会不同，但失败模式是通用的。

## A. 数据层

### A1. 盘中补跑把"今天的盘中价"当成"昨天的收盘"写进日线库（最严重）

**现象**：前一晚的收盘任务漏跑，次日盘中补跑日线增量脚本：搜狐沪深300 日线最新仍是上一个交易日 D，旧闸门（"D 等于今天且未到 15:30"）拦不住——D 不是今天。脚本拉了**新浪全市场快照**，而工作日 09:15—15:30 的新浪快照是**今天的盘中价**，于是把今天盘中价追加成"D 的收盘"。同时快照里的"前收"（其实是 D 的真收盘）与库里 D-1 的收盘对不上 → 脚本判定这是"除权除息"，**对全市场个股整段历史按假系数重算前复权**。随后纸面账户用假数据推进，假买、假卖，写出假的档位文件。

**根因**：日线增量把"快照日期"与"指数交易日"当成同一天；除权检测没有大面积异常保护。

**修复**（现场全量备份 → 删假行并按上一日的 `adj` 反除 → 搜狐补真数据 → 用"还原状态＋假数据按原代码复演必须逐字段重现事故文件"自证还原正确）。

**加的两道闸门（`daily_update.py`，本仓库已内置）**：
1. 工作日 **09:15—15:30 一律不写**日线；
2. 快照"前收"与库里上一日收盘**大面积对不上（>20%）整次不写**（正常只有几十只当天除权的票）。

**漏掉的交易日怎么补**：`catchup_lastday.py`（只用搜狐已收盘日线，盘中也能安全跑）→ `regime_daily.py` 出该日档位。

**如何避免**：①任何"增量写库"脚本，写之前先问"这批数据真的是我以为的那一天吗"，用一个**独立的对账量**（这里是前收对不上的比例）做闸门；②备份先于修复；③修复用"复演自证"，不要靠"看起来对"。

### A2. 档位文件用不完整的日线算出，写出"修复期、宽度 50%"

**现象**：日线增量在盘中两次补跑前一交易日，都被 A1 的第二道闸门拦下（日志：`aborted=prev_close_mismatch`，快照前收与库里上一日收盘大面积对不上——因为那时新浪快照已经是当天的行情，不是目标日的），个股日线没追加；而指数日历被另一路径补到了目标日。此时跑档位，个股侧没有目标日的数据，宽度分母为 0，代码落到默认值 `0.5`，档位文件写成 `state_bt=修复期、breadth_full_market=0.5`（宽度恰好是 0.5 就是默认分支的指纹）。`v51_scan` 读 `日期 < 当日` 的最新档位文件 → 受影响日的仓位上限/倍率会用错。
**修复**：用搜狐按目标日补齐个股日线后（`backfill_sohu_batch.py` 以 `TARGET=<目标日>` 跑），再重算档位覆盖坏文件。
**本仓库的防护**：`regime_daily.py` 写入前检查"最新一天有效个股数 ≥ max(1000, 前 10 日中位×0.9)"，否则 `REGIME_ABORT` 并**不写文件**；`_common.regime_before()` 读档位时也会跳过 `diag.n_valid < 1000` 的坏文件、回退到更早一份。
**如何避免**：默认值（`0.5`、"修复期"）是危险的——"没数据"和"数据说中间"必须区分；有数据依赖的产物写之前要自检覆盖率。

### A3. baostock 30 分钟历史被静默截断

整段请求下，个别票返回到某一年就停（实例：一只只到 2021-01-12 共 2000 根，一只只到 2024-02-22 共 8000 根），下载器和检查脚本都不报错。**新池/新票上线前一律跑 `m30_data.py check`**（每个交易日应有 8 根、对日线交易日历无缺口、收盘/最高/最低与日线一致），不通过的用 `m30_data.py fix`（按年分段重下，覆盖 ≥99% 且末日对才替换，旧文件备份）。已知数据源本身缺 1 天的票有若干只（不是你的错，不用反复重下）。

### A4. 数据合并的类型坑（K 线重复）

CSV 读进来 `time` 是整数（`1000`），实时源是字符串（`"1000"`）。先 `concat` 再 `drop_duplicates(["date","time"])` 去重失败 → 每只多出 11 根重复 K 线 → 均线/MACD/打分全偏。**修法**：合并前先把各来源的 `date` 统一成 `str`、`time` 统一成 `"%04d"`，去重后 `assert not duplicated`。

### A5. 次新股、除权除息、复权口径

- 引擎用前复权价（不复权价 × 日线 `adj`）；挂单用真实价；失效价随 `adj` 换算。
- 妙想均线是前复权而收盘价不复权：除息后若要把止损位当挂单价，必须用真实价自算 MA20。
- 搜狐不复权行 + 官方前收反推前复权：当日前收 ≠ 库里上一日不复权收盘 ⇒ 当日除权，整段历史按比例重算 `adj`。

### A6. 搜狐/新浪/东财取数的稳定性（实测）

新浪 30 分钟较稳、耗时短；东财约一半连接被断；搜狐日线补数一次 40 码约 50 秒。**新浪主、东财备**。数据源失败要在【数据健康】里如实报告，**不要自行换数据源**。

## B. 引擎层

### B1. 线段"永久卡死"缺陷

见 [02](02-engine-spec.md) 第 3 节第 4 点。影响：原池 64 只里 40 只、256 只回测样本里 160 只、全市场约 62% 的票整段 0 事件。**修复前的所有 V5.x 回测数字作废，以修复后的复跑为准**（[08](08-backtest-evidence.md)）。教训：
- "0 个信号"本身是需要审计的数据。一周 0 信号，必须区分"市场里确实没有"和"引擎看不见"。**发现手段**：用独立的第二条代码路径（`pool_watch` 里的本地修正版 `Walker2`）和主路径（`v51_scan`）对同一批票做对账，两边事件不一致 ⇒ 有 bug。
- 修引擎的流程：先备份原文件（留 md5）→ 修 → 未卡死的票修复前后**逐事件相同**（证明只改了该改的）→ 截断重算 48 组 0 差异（证明没有前视）→ 复现关卡（修复前引擎重跑旧流水线逐笔复现旧结果）→ 再复跑回测。
- 本仓库 `tests/test_engine_truncation.py` 里有 Walker 卡死的回归用例，突变检验已验证"还原缺陷"会被抓住。

## C. 定时任务与执行环境

见 [07](07-scheduled-tasks.md) 第 4 节（会话卡住、集中补跑、并发上限、网关超时、执行通道 60 秒限制）。

### C1. 会话卡住的排查顺序

1. `list_scheduled_tasks`：看 `lastRunAt / nextRunAt`——卡住时 `nextRunAt` 会直接跳过一个周期；
2. 会话列表里同名会话是不是一直 `running`；
3. 账本文件 `live/state/v51_ledger.json` 的 mtime；
4. **只读**的 `pool_watch.py` 可以照跑（拿到结论先回），**不要**在卡住的会话可能突然恢复时自己跑 `v51_scan.py` 写正式账本（可能两个进程同时写 JSON）；
5. 请使用者点开会话看是不是在等工具授权；必要时手动停掉。

## D. 业务口径

### D1. "退潮期"与 hard 的误读

hard 不是第五档（见 [01](01-trading-rules.md) 第 4 节）。**使用者问"为什么不开仓"时，先看最新档位文件的 `state_bt`，再算 r126**。hard 触发线＝沪深300 的 0.85 × 126 个交易日前收盘；126 日按**行**数，不是日历日（日线库里指数的行数要核对）。

### D2. 主题簇、1.5a 与"入池 ≠ 可买"

见 [03](03-stock-screening.md)、[05](05-pool-file-contract.md)。曾因不查 1.5a，一只科创板票在池内躺了约 3 个月才被批量核出收盘价始终高于天花板。

### D3. 冷却期少算一天

把"冷却至 X 日"读成"X 日前可买"，少算了一天，造成一次违规买入。**必须逐日列出交易日**（`pool_tool.py cooldown`）。责任在文件写法，不是执行纪律——所以立规则：禁止写"冷却至 X"。

### D4. 质地 C 的票挡不挡 V5.1

V2.6 的"质地 C 仅研究观察、不开新仓"写给买点 A/B；V5.1 附录把九道闸门随买点 A/B/C 一并停用、第 3 章股票池也没有质地关卡 → **现状：V5.1 实时回测照常记录质地 C 票的买点**。这是**待使用者裁定**的口径缺口，不是已决定的规则；裁定前不要擅自在代码里加这道闸门（会改变回测与实时的一致性）。

### D5. 财报季的验证点

池内票的三季报/年报披露日是质地复核点；披露前后股价跳空常打穿失效价。**实例（已泛化为比例）**：一只创业板票买入次日恰逢三季报，开盘直接跳空开在失效价下方（约 −4.4%），第一根 30 分钟收盘低于失效价，按手册"当根收盘确认、下一根开盘卖出"，实际成交价比失效价低约 5%，亏损约 **2.0R**（计划是 1R）。其中开盘缺口约占 0.2R，开盘后前 30 分钟继续下跌约占 0.8R。**失效价不是成交价**：计划损失要按"风险预算×(1+0.2)"预留，财报前后的持仓尤其如此；回测里止损单平均多亏 0.15—0.24R，约 7%—13% 的止损单亏损超过 1.5R。

## E. 汇报与协作

### E1. 盘中"能买什么"拖延

汇报应先给可执行结论、再补核对：先快答（买点＋限价＋失效价＋股数＋最要紧一条风险），再补核对（[10](10-discipline-and-verification.md)）。若先跑一长串核对再开口，可能错过当日执行窗口。**纪律**：先快答，后补全。

### E2. 回复编号歧义

按序号指代任务容易产生歧义（"第二个""第四个"可能指不同范围的列表）。**纪律**：删除前后都明确说出删了哪几个任务名；拿不准时宁可只动自己新建的。

### E3. 排行榜的"提示不咬人"

见 [03](03-stock-screening.md) 第 5.3 节。

## F. 代理与网络（macOS 常见）

- A 股数据源（新浪/东财/搜狐/baostock）通常**应直连**；系统代理对其路由不当会断流。
- 若遇到 `SSL: CERTIFICATE_VERIFY_FAILED`：给 Python 配证书（`certifi`），不要关闭校验；Mac 的 python.org 版本需要运行一次 `Install Certificates.command`。
- 遇到 `GitHub/Google` 不通但 A 股数据正常，多半是代理的"国外流量"节点问题，与本工具链无关。

## G. 值得写进每次汇报的"数据健康"检查单

1. 最后一根 K 线时间是否 = 当前应有的最新一根？
2. 取数源各取到几只、失败几只（及原因）？
3. 落后于最新 K 线的票有几只？
4. 档位文件的日期与来源？`diag.n_valid`（有效个股数）是否正常（≥1000）？
5. 引擎 md5 是否是含修复的版本？
6. 日线库最后一日是否 = 最近一个已收盘交易日？
7. 信号延迟记录里 >30 分钟的有几个？
