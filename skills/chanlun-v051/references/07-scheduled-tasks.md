# 07 · 定时任务：设计、安装与运维

模板在 `assets/scheduled-tasks/`，渲染用 `scripts/install_tasks.py`。本章讲**为什么这样设计**和**怎么运维**——后者来自常见运维翻车场景。

## 1. 任务清单与设计取舍

| 任务 | 时间（本地，工作日） | 池 | 说明 |
|---|---|---|---|
| `v51-intraday-am-pm` | 10:02 10:32 11:02 11:32 14:02 14:32 | 关注池 | 每根 30 分钟 K 线收盘后跑扫描并汇报 |
| `v51-intraday-1332` | 13:32 | 关注池 | 13:30 那根（午休后第一根）单独成任务，否则要到 14:02 才发现 |
| `v51-intraday-1502` | 15:02 | 关注池 | 15:00 最后一根；**列次日 9:30 待执行单** |
| `v51-close-1835` | 18:35 | 关注池 | 日线增量 → 档位 → 扫描 → （可选）TRIN → 日报 |
| `focus-intraday-am-pm` | 10:07 10:37 11:07 11:37 14:07 14:37 | 重点池 | 晚 5 分钟，避免两个扫描同时压机器 |
| `focus-intraday-1507` | 15:07 | 重点池 | 15:00 最后一根，重点池 |

**为什么 :02/:32**：新浪的 30 分钟 K 线在收盘后几秒到几十秒才推出；`:02` 留出缓冲，脚本自带 +8 秒的"已收盘"判定缓冲。
**为什么重点池不配 13:37 和收盘日报**：账本是整段重放，漏跑不丢记录；任务多了只增加每天要读的回复数。**新建任务宁少勿多**。代价：重点池 13:30 那根的信号晚约 37 分钟发现，日报"信号延迟记录"会如实标出；没有单独的收盘日报（15:07 那次已带次日待执行单）。
**新池要建任务时的做法**：盘中一个多点任务＋收盘最后一根一个，通常够用；只有明确要求才加。删任务时明确说出删了哪几个，别动原有的。

## 2. 安装

```bash
python3 scripts/install_tasks.py --home ~/a-share-v51 --address 你 --focus-n 100 --focus-start YYYY-MM-DD --nav 200000
# 渲染结果在 ~/a-share-v51/tasks_rendered/*.md，frontmatter 里有 cron
```

- **桌面助手的定时任务**：把每个渲染文件的正文作为任务提示词、cron 取 frontmatter 里的值创建。**创建后每个任务点一次 "Run now"**（首次运行常需要点工具授权；不预授权，无人值守时会被自动拒绝）。
- **不想用助手**：`install_tasks.py --crontab` 打印可直接粘进 `crontab -e` 的脚本版——账本、日报、信号日志都是脚本写的，助手只负责"读结果、写汇报"。
- 任务提示词里**不放规则**（规则在脚本和 references 里），所以改规则不用改任务。

## 3. 汇报格式与"不编造"纪律

- 收盘与 15:02 任务以**单独高亮的【整理结论】块**开头（引用块＋粗体标题＋反引号包住核心结论），再写【依据】【推论逻辑】【数据健康与局限】。盘中任务用【结论】【依据】【推论逻辑】【数据健康与局限】，约 12—15 行。
- **所有数字必须来自脚本输出和报告文件**；读不到就写"报告未提供"；不编造、不凭记忆补数。
- **不给投资建议**：只做事实解读与规则推演，不说"该买该卖"。
- 失败时报告原因，**不要自行换数据源**。
- TRIN 观察指标只陈述事实，**不引申成"冰点/超买/可满仓"**，不参与任何规则（实时回测期不改规则）。

## 4. 实测踩过的坑（必读）

**① 任务会话卡住，下一次被跳过**。现象：盘中任务会话停在某个工具调用（宿主机脚本调用后的沙箱命令、通知调用后），账本没更新；"上一次没结束时同一任务的下一次会被跳过"，于是当天后面的扫描全没了（最严重时账本停在上午某根 K 线，当日买点与止损单都没执行）。规律：卡点几乎都在沙箱 bash / 通知这类工具调用上，而脚本本身能跑。
- **排查顺序**：`list_scheduled_tasks` 看 `lastRunAt/nextRunAt` → 会话列表里同名会话是不是一直 running → 账本 mtime。**先用工具实查，别先猜原因**。
- **不要在卡住的会话可能突然恢复时自己跑 `v51_scan` 写正式账本**（可能两个进程同时写 JSON）；只读的 `pool_watch` 可以照跑。
- 夜里任务会被休眠冻住、早上自己续跑；早上看到昨晚的会话还 running 先别动，等它跑完。
- 一个降低风险的做法：**盘中任务里尽量少依赖"沙箱 bash"**，脚本调用 + 读文件 + 回复即可；落盘等"可选"步骤放最后，失败不影响结论。

**② 应用关闭/睡眠后集中补跑**：醒来后多个任务可能同一秒一起启动（实例：多个任务同一秒启动，同时段出现网关错误）。注意并发。

**③ 本机并发上限 ≤3**：同时挂的重计算后台进程（回测、事件层脚本等）**不要超过 3 个**，否则宿主机桥接卡死、所有工具调用超时（并发过多时每个调用都超时，会话断掉）。队列并发设 2—3；长任务一律后台＋状态文件/DONE 标记，结果落盘，断线也能续。

**④ 网关/中转超时（502、upstream timeout）**：多为"中转→上游"超时，不是额度；与任务成批补跑同型。红色错误卡片是间歇事件，编辑重发即可，别急着换会话。

**⑤ 首个宿主机调用慢**：收盘任务第一步（日线增量）可能跑十几分钟（实测可能跑十几分钟）；其它任务读日线库要等它。

**⑥ 执行通道单次 ~60 秒超时、且不能传参**：长任务用无参启动器 + `bg_run.py` 后台跑、日志落盘。

## 5. 落盘与审计（可选）

每次运行把最终回复原样写成 `journal/…/<STAMP>_<简称>.md`，**STAMP 用本机时钟（`now.py`）**，不要用容器/沙箱时钟。好处：漏看的回复事后能查；"信号当时说了什么"可审计。
文件头建议固定：任务 ID、运行时间（本机时钟）、来源、性质（"V5.1 纸面实时回测，不下真单，不构成投资建议"）。
上传到笔记/知识库是使用者自己的扩展，不在本技能范围内。

## 6. 起点日与具名例外

任务只是执行器。**实时回测的起点日、阶段系数、是否进小仓，是使用者的裁定**，不是任务的决定；定时任务期间任何人（包括助手）都不得根据新的回测结果改买卖规则（手册 10.1）。见 [09](09-rollout-and-acceptance.md)。
